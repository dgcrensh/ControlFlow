# From vector editor to 2.5D character modeler: the gap (reviewed on main at c9afc2e, from code and docs only, nothing run on a device)

Effort: S small, M medium, L large, XL several milestones. "Have" means shipped on main today.

## The short answer

The gap is wide, but it is mostly *above* the layer that exists, not instead of it. Character Studio today is a
strong vector editor with a rest-pose skeleton: drawing, editing, appearance, layering, bones in Setup mode, and a
stable, documented file format. Nothing yet moves the art: there is no posing, no binding beyond "this part is on
this bone", no deformation, no parameters, no physics and no playback. Those are exactly the layers a 2.5D modeler
is made of.

The good news is that the foundation fits the job better than most vector editors would. Attachments are already
stored in bone space, per-point `weights` are reserved in the format, variable width lives on the centerline so it
survives bending, the core is UI-free and tested, and `LiveTransform` already draws moved shapes through a GPU
transform without re-tessellating. The hard new problems are (1) a parameter and keyform system, which is the heart
of 2.5D, and (2) a renderer that can redraw deforming vector paths every frame, which the current cache-once design
does not do.

## What "2.5D character modeler" means here

There is no single standard, so this review uses three reference points and the features they share:

- **Live2D Cubism** (the defining 2.5D tool): named parameters (`AngleX`, `AngleY`, `EyeLOpen`, `MouthOpen`...)
  drive deformers. Art is drawn front-on, then reshaped at keyforms (for example head turned 30 degrees left and
  right, up and down), and the runtime blends between keyforms, including in 2D grids (X and Y together). Warp
  (lattice) and rotation deformers nest in a tree. Draw order, opacity and visibility can change with a parameter,
  so an ear can slip behind the head as it turns. Physics turns parameter motion into hair and cloth sway.
- **Spine** (skeletal 2D): bones, FK and IK, weighted mesh skinning, path and transform constraints, skins and
  attachment swaps, a timeline with curves, and a small runtime in many engines. "2.5D" in Spine comes from mesh
  deformation and draw-order keys rather than parameters.
- **Moho and Cartoon Animator (360 Head)**: the vector-native take. Vector points are bound to bones; "smart bones"
  or angle keys morph the vector art between hand-drawn views, and sprite switches swap parts that change too much
  (a nose seen from the side). This is the closest match to a vector-only tool.

Common to all three, a 2.5D modeler needs: a posed skeleton, deformation of the art, parameters with keyforms and
blending, parameter-driven draw order and visibility, part swaps, secondary motion, a preview or playback mode, and a
runtime file another program can play.

## The gap, layer by layer

### 1. Pose the rig: finish milestone 5 (M-L)

Pose mode with FK, rigid binding applied to rendering, a reset button and a few saved test poses (the format
already reserves `poses`). The renderer can draw rigidly bound parts through a per-part affine, extending what
`LiveTransform` does for drags, so posing a cutout character needs no re-tessellation. This is the spec's v1
finish line and the base everything below stands on.

### 2. Bend the art: weighted vector skinning and IK (L)

Per-point `[bone, weight]` pairs (already in the format), auto-assigned by distance and then painted, as the spec
decided. Skinning a Bézier point means transforming the anchor and both handles by the blended bone transforms.
This is the first feature that changes path geometry every frame, so it forces the rendering work in section 6.
Two-bone IK for limbs and a target bone are the usual companions (the spec lists IK as "later").

### 3. Parameters and keyforms: the heart of 2.5D (XL)

This is the feature that makes a character turn its head rather than just swing its limbs, and nothing in the code
leans toward it yet. It needs:

- **Parameters** on the character: name, range, default (`AngleX` -30 to 30, `EyeOpen` 0 to 1).
- **Keyforms**: for a part (or deformer), stored shapes at chosen parameter values. With vector art the natural
  keyform is a set of point offsets (anchor and handle deltas) from the rest drawing, which only works while the
  point count and order match. So editing at a keyform must lock topology, and adding or removing a point must
  update every keyform of that shape.
- **Blending**: linear between keys on one parameter, bilinear on a grid of two (head X and Y), additive or
  multiplicative across independent parameters.
- **Editing UX**: pick a parameter value, then draw or direct-select at that value and the edit lands in the
  keyform, with onion skin of the neighbouring keys. Mirroring a keyform across `.L`/`.R` saves half the work.
- **Parametric draw order and visibility**: per-key `drawOrder` overrides and per-key opacity, so the far eye and
  ear can fade or tuck behind the face as it turns. The current `behindSlot` model is static.
- **Undo and size**: keyforms multiply the drawing's size; undo stores whole `Drawing` snapshots (risk noted in
  full-editor-slate.md for variants too).

### 4. Deformers (L)

Live2D's warp deformer (a lattice that bends everything inside it) and rotation deformer (a pivot that turns its
children) let one keyform move many parts together, which is how a whole face shifts on `AngleX` without keying
every shape. For vector art a warp deformer maps each point and handle through a bicubic lattice. They nest, so the
deformer tree sits beside the bone tree and parts bind to either.

### 5. Turnaround authoring (L)

What makes 2.5D practical rather than tedious: a reference sheet per angle (reference images exist and help here),
a "draw at this angle" flow that seeds a keyform from the front view, part swaps for features that change shape
too much to morph (side-view nose, profile mouth), and a curved-surface helper that wraps a flat face over a sphere
or cylinder to fake the first few degrees of turn. Variant per part (full-editor-slate #20) is the swap half of this.

### 6. Rendering deforming vectors at 120 Hz (L, the main technical risk)

Today a shape is flattened and tessellated once, cached by zoom bucket, and only edits re-tessellate. With bones,
weights, keyforms and deformers, every visible point can move every frame. Options, roughly in order of effort:

- **Rigid parts on the GPU** (section 1): a transform per part, no re-tessellation. Covers cutout posing.
- **Re-flatten on the CPU per frame**, reusing the parallel tessellation and reserve work from the performance plan.
  Likely fine for a modest character, needs measuring on the stress drawing with every point moving.
- **Deform the triangles, not the curves**: tessellate in rest pose with per-vertex bone weights and keyform deltas,
  and skin on the GPU, as a mesh renderer would. Fast, but outlines and variable width thin or fatten under strong
  bends and need a re-tessellation threshold (as `LiveTransform.maximumScale` already does for drags).

The performance audit and plans assume static geometry, so this needs its own plan before section 2 lands.

### 7. Secondary motion: physics (M)

Pendulum chains whose input is a parameter or bone angle and whose output drives another parameter or bone (hair
tips, earrings, a tail). Small to build once parameters exist; useless before.

### 8. Playback and animation (L, may belong to the separate animation system)

A parameter panel with sliders and a test-pose library is the modeler's own preview and is in scope. A timeline
with keys and curves is what the spec calls the future animation system. Worth deciding whether that system lives
in this app or reads the file elsewhere.

### 9. Format and runtime (M-L)

The 0.2 format is already close to Spine's structure, which makes a **Spine JSON export** a realistic way to play
characters in existing engines for posing and skinning (vector shapes would need converting to meshes). Live2D's
`.moc3` is proprietary and not a realistic target. Parameters, keyforms, deformers and physics need new keys and a
format bump, and a reference player (CharacterCore already has the math and runs on Linux) so the format can be
tested end to end.

## Decisions that shape the plan

The owner confirmed the defaults below on 2026-10-12: Live2D-style, vector only, parameter preview here and timeline later.

1. **Which 2.5D.** Live2D-style (front-facing art that turns roughly ±30 degrees through keyforms and deformers)
   versus full turnaround (Cartoon Animator style, many drawn angles with swaps). **My default: Live2D-style**,
   because it builds on one drawing per part and the existing bone-space model; full turnaround can come later as
   swaps on top.
2. **Vector or raster.** The spec says vector only "for now". Every reference tool except Moho deforms textured
   meshes. **My default: stay vector**, deforming Bézier points directly. It keeps the editor's strength and the
   file format, at the cost of the rendering work in section 6.
3. **Where playback lives.** In this app, or in the separate animation system the spec describes. **My default:**
   parameter preview and test poses here; timeline elsewhere until the modeler is solid.

## Recommended order

The milestone plan built from this order is [2.5d-roadmap.md](2.5d-roadmap.md).

1. Milestone 5 as specced: Pose mode, FK, rigid binding on the GPU, test poses. (M-L)
2. A rendering plan for deforming paths, measured on the stress drawing, before weights land. (S to write, L to build)
3. Two-bone weights with auto-weights and painting; IK for limbs. (L)
4. Parameters and keyforms on points, with a slider panel, then parametric draw order and opacity. (XL)
5. Variants per part (full-editor-slate #20) as swaps by parameter. (M)
6. Warp and rotation deformers. (L)
7. Physics. (M)
8. Format bump, reference player, Spine export. (M-L)

Steps 1 and 3 are already the spec's plan; 2 is new and gates 3; 4 is where the app becomes a 2.5D modeler.

## Risks

- **Topology and keyforms.** Vector keyforms rely on matching point lists. Every editing command that adds, removes
  or reorders points (insert point, simplify, booleans later, join, split) must update or invalidate keyforms.
- **Rendering cost.** Section 6. Measure before committing to an approach.
- **Undo memory.** Keyforms and variants multiply snapshot size; bounded undo (performance audit #7) matters more.
- **Byte-stable format.** The new keys must stay optional and ordered, with a migration if the version moves.
